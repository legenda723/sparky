# Спарки — правила работы

Личное PWA с флеш-карточками (английский, FSRS, геймификация в духе Duolingo) для iPhone 16 владельца.
**Что строим — в SPEC.md. Читай его в начале каждой сессии.** Текущий этап — первый незакрытый `[ ]` в разделе 9.
**Как выглядит — в DESIGN.md.** Читай его перед любой работой с интерфейсом.

## Владелец
- Ноль опыта в программировании. Он проверяет результат и говорит, что поменять. Код он не читает и не правит.
- Общайся **по-русски, простыми словами**. Технический термин — только с объяснением в скобках.
- Когда нужно действие владельца (одобрить команду, войти в GitHub, проверить на iPhone) — дай нумерованные шаги «что нажать».
- Продуктовые мелочи решай сам и записывай в SPEC.md → «Решения». Спрашивай только о том, что сложно переделать.

## Порядок работы
- **Один этап — одна сессия.** Начинай с плана простыми словами и жди одобрения. Для этапа есть команда `/etap N`.
- Делай маленькими шагами. После каждого шага: `npm run typecheck`, `npm test`, `npm run build`.
- Любое изменение интерфейса — проверь во встроенном браузере на **393×852** (iPhone 16), светлая и тёмная тема. Покажи скриншот. «Готово» = есть доказательство, а не «должно работать».
- В конце этапа пройди его чек-лист «Готово, когда» по пунктам: ✅ с доказательством или ❌.
- Итоговый коммит этапа — после «ок» владельца (промежуточные — см. «Лимиты подписки»). Потом отметь этап `[x]` в SPEC.md и допиши раздел 12.
- Новые идеи владельца по ходу — в SPEC.md → «Потом», не в текущий этап (если он сам не скажет «сейчас»).
- Если одно и то же не получилось исправить за 2 попытки — остановись, объясни причину и предложи начать новую сессию с уточнённой задачей.
- Если владелец поправил твою ошибку — добавь сюда короткое правило в раздел «Уроки», чтобы не повторять.

## Стек
Vite + React + TypeScript (strict), Tailwind v4 + CSS-переменные, Motion, Dexie (IndexedDB), ts-fsrs 5.x, zod, vite-plugin-pwa, web-haptics, lucide-react, @fontsource/nunito, Vitest. Деплой: GitHub Actions → GitHub Pages.
- Новую зависимость добавляй только с понятной причиной, и скажи владельцу, зачем она.
- Документацию библиотек бери актуальную (context7, если он установлен; иначе — официальный сайт библиотеки), а не по памяти.

## Данные — святое
- Схема Dexie меняется **только** новой версией с миграцией и тестом миграции. Никогда не удаляй и не очищай базу в коде — кроме двух действий владельца: «Сбросить всё» и «Заменить всё» при восстановлении, и только после предложения сохранить бэкап.
- Удаление карточек и колод — мягкое (`deletedAt`): журнал оценок и медиа не стираются.
- Каждый ответ в уроке сохраняется сразу, одной транзакцией.
- Формат бэкапа версионирован; тест «экспорт → импорт = те же данные» всегда зелёный.
- Никаких сетевых запросов с данными владельца, никакой аналитики и трекеров.

## Код
- Логика SRS — только в `src/srs/`, чистые функции с тестами. UI не зовёт ts-fsrs напрямую.
- Все даты — через `dayKey()` (день начинается в 04:00 по местному времени).
- Компоненты маленькие. Тексты интерфейса — по-русски.

## iPhone
- safe-area отступы, `100dvh`, поля ввода ≥ 16px, `touch-action: manipulation`, нет эффектов только по наведению.
- Озвучка (`speechSynthesis`) и звуки — только после касания. Аудио в режиме «ambient».
- Вибрация — только через web-haptics и только в ответ на действие; если не работает — тихо отключить.

## Дизайн
- Только токены и компоненты из DESIGN.md. Нужно новое — сначала допиши в DESIGN.md.
- Отклик на каждое касание: анимация + звук + вибрация. Учитывай prefers-reduced-motion.
- Если владелец прислал образец (скриншот или файл в `references/`) — работай циклом: сверстал → скриншот 393×852 → сравнил с образцом → список отличий → поправил. Берём раскладку и размеры, а цвета, маскота и тексты — свои.
- Duolingo — ориентир по ощущениям. **Нельзя:** название/логотип Duolingo, сова Duo, шрифт Feather, их картинки и звуки. У нас свой маскот Спарки.

## Git
- Сообщения коммитов — по-русски, коротко. Никогда `push --force`. Не коммить секреты и личные бэкапы.

## Лимиты подписки
У владельца план Pro: лимит на 5 часов и недельный лимит, общие с обычным чатом. Остаток ты не видишь, поэтому:
- Не экономь на качестве: проверки, тесты и скриншоты не пропускай.
- Экономь там, где это бесплатно: читай только нужные файлы, не перечитывай одно и то же, не держи без нужды запущенные процессы. Субагентам для поиска и проверок давай модель Sonnet и запускай их по одному-два (в `/polish` тоже — заходами по два, встроенный браузер у всех общий).
- Этап может оборваться на лимите. После каждого законченного шага делай промежуточный коммит и обновляй в SPEC.md (раздел 12) строку «В процессе: этап N — сделано …, дальше …», чтобы новая сессия продолжила с того же места.

## Длинные сессии
При сжатии контекста всегда сохраняй: номер этапа, что уже сделано, что осталось по чек-листу, изменённые файлы, нерешённые ошибки.

## Команды
`npm run dev` · `npm run build` · `npm run preview` · `npm run typecheck` · `npm test`

## Уроки
(Сюда добавляются правила после ошибок.)
- iOS 26 в веб-приложении на экране Домой занижает высоту экрана (ошибка WebKit); браузер на компьютере этого не показывает. Высоту экрана задаём только через правила в `index.css` (`display-mode: standalone`), раскладку низа экрана подтверждает владелец на iPhone.
- Анимации нажатия и переходов — мягкие: отклик в момент касания, без «скачков» по ключевым кадрам и без наложения двух сдвигающихся экранов (DESIGN.md → «Движение»).
- Ответ владельцу (план, список, вопросы) всегда пиши текстом в чат. Окошко с кнопками — только короткий итог и вопрос, оно может закрыться.
